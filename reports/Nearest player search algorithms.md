# Adaptive leaves and thresholds remove the pile's N²

The 25 m pile is quadratic because the grid's leaf is the wrong size, and the selection code multiplies that mistake. Every client pushes all ~10k players into a vector and partially sorts it three times. Exotic all-kNN algorithms don't fix this. Two changes inside the existing `Grid` do. **First, make selection incremental and cheap**: packed `u64` keys, a running k-th threshold, truncate-to-k, and positions stored inline in the grid. In a local single-threaded benchmark this cut per-candidate cost **about 3–5×** (6.5 ns → 1.3–2.5 ns), but it leaves O(N) candidates per query. **Second, give dense cells density-adaptive sub-cells and prune by box distance.** This is the "leaf-based" search that the parallel-kNN literature shows reaches expected **O(k log k) per query, independent of N** ([Yesantharao et al. 2021](https://ar5iv.labs.arxiv.org/html/2111.04182)). By this report's arithmetic it cuts a pile query from ~10,000 candidates to ~300–800. Together these should bring pile assembly from **43 ms down to roughly the 200 m disk's ~4 ms** (derived, not measured). The rest is nice-to-have, in this order: a temporal seed for the threshold, per-leaf shared candidate sets, then approximate caps. No shipped engine found does exact per-client kNN at all. Unreal Iris, Replication Graph, Mirror and Photon all use coarse shared cells plus a priority accumulator, so approximation is a legitimate ladder rung. But the exact fix is cheap enough that approximation should only be a safety net. It is needed in one case: players stacked on *identical* positions, which no subdivision can separate, and the sim has no player collision.

**Evidence key.** Linked claims are from published sources. Claims marked *(derived)* are arithmetic or reasoning by the researchers or this report, not measurements. Claims marked *(local bench)* come from the companion single-threaded microbenchmark `research_notes/Nearest player search algorithms/cache_simd_selection_bench.rs`, run on the WSL2 dev box (Ryzen 7 5700X3D, Zen 3), not the EPYC 8534P. Its ratios are indicative, and its absolute nanoseconds don't transfer. Repo facts cite file paths.

## The pile pushes ~10,000 candidates and selects three times per client

The code makes the cost easy to read. The pile spawns into `disk:25`, a disk of 25 m **radius** centred at (4096, 4096) (`sim/src/server.rs` `pick_spawn`; `WORLD_SIZE` = 8192). That centre is exactly a corner of the 32 m near grid, so the pile sits in four cells of ~2,500 players each. `walk_rings` (`sim/src/grid.rs`) visits ring 0, the client's own quadrant, and the `assemble` visitor (`server.rs` ~L1000–1020) pushes every in-radius player as a `(f32, f32, u16)` tuple. At `Done(0)` it runs `select_nth_unstable_by(total_cmp)` over ~2,500 entries. The 100th distance exceeds the ring-0 bound of 0, so ring 1 is walked, which pushes the other three quadrants, and the full ~10k vector is selected again at `Done(32)`. After the walk a third `select_nth_unstable_by(k)` runs over all 10k. The vector is never truncated mid-walk. The mid tier then repeats the pattern on the 64 m `mid_grid`, over the ~1/3 of players due that tick. The bare-metal limits run shows the result: assembly grows 1.7 → 8.8 → 23.0 → 43.1 ms at 1.2k → 4.2k → 7.2k → 10k players. Tick p99 crosses 33.3 ms at **7,217 players**, and the profile puts **46% of CPU in `select_nth_unstable` and 14% in the grid walk** (`baselines/2026-10-04-scaleway-limits/summary.md`, `sim/README.md`).

One correction to the research notes: they assumed a 25 m *diameter* (~20 players/m², 100th neighbour at 1.26 m). With the code's 25 m radius, the density is **~5.1 players/m² and the 100th neighbour sits at ≈2.5 m** *(derived: √(100 / (5.1π)))*. The 150th sits at ≈3.1 m. The conclusions survive, and the sizes below use the corrected numbers. Either way, a 32 m cell is an order of magnitude too coarse for the local interaction length. The k-th distance in this workload varies by more than two orders of magnitude: ~2.5 m in the pile, ~10 m in the 200 m disk at 10k, and radius-limited at 150 m in the uniform spread, where only ~11 players fall inside the near radius *(derived)*. Simulation codes avoid exactly this mismatch by tying cell size to the interaction length or the density. SPH uses cell = support radius, giving ~30–40 neighbours ([Koschier et al.](https://ar5iv.labs.arxiv.org/html/2009.06944)), and GROMACS sizes its grid from density so each cell holds a fixed particle count ([Páll & Hess 2013](https://ar5iv.labs.arxiv.org/html/1306.1737)).

Two smaller inefficiencies compound the cost. The ring bound `Done(k·cell)` is conservative: the true lower bound on unvisited items is the query's distance to the nearest edge of the visited box, which lies between k·cell and (k+1)·cell, so a whole ring is often walked needlessly *(derived)*. And every candidate costs an indirection: positions are read from `bodies[j].state.pos` rather than stored in the grid.

## Packed keys and a running threshold buy ~5×, not an asymptote

The hardware-level fixes are worth doing first because they are small, exact and local. The table summarises the local bench: one query, k = 100, ids randomly permuted relative to the body array to mimic the grid's indirection.

| variant (n = 600 / 3,000 / 10,000 candidates) | ns per query | ns per candidate |
|---|---|---|
| Current: AoS gather via id, `(f32,f32,u16)` tuples, two `total_cmp` selects | 3,988 / 19,072 / 65,199 | ~6.4–6.7 |
| Distance only, AoS gather | 370 / 2,234 / 7,721 | 0.62–0.77 |
| Distance only, SoA `x[]`/`y[]` contiguous | 31 / 212 / 854 | 0.05–0.09 |
| SoA + packed `u64` key `(d2.to_bits()<<32 \| id)` + one select | 1,500 / 6,585 / 21,496 | 2.2–2.5 |
| SoA + branchless keys, then threshold buffer (4k, select-and-truncate) | 1,638 / 6,043 / 13,366 | 1.3–2.7 |
| SoA + u16 quantised d² + 256-bin histogram select | 1,559 / 5,415 / 17,142 | 1.7–2.6 |
| SoA + `BinaryHeap<u64>` bounded to k | 6,055 / 13,374 / 24,362 | 2.4–10 |

*(local bench)* Three lessons follow. First, **selection, not distance, dominates today.** The gather costs ~0.7 ns of the ~6.5 ns per candidate. With everything L2-resident (10k × 28 B bodies is 280 KB), the rest goes to comparator closures over 12-byte tuples and mispredicted partition branches. Mispredictions are the known dominant hidden cost of quickselect-family partitioning ([Brodal, AU slides](https://cs.au.dk/~gerth/ae15/slides/branch-mispredictions.pdf)). Second, **a packed integer key plus a running threshold wins.** Non-negative f32 bit patterns order like integers, so `(d2_bits << 32 | id)` turns selection into plain `u64` work with deterministic tie-breaks. A threshold that holds the k-th key rejects most candidates with one compare. The threshold buffer beat a single select by 18–38% at n = 10k and was **4.9× faster than the current code**. A bounded binary heap, the RVO2-style instinct ([RVO2 Agent.cc](https://github.com/snape/RVO2/blob/main/src/Agent.cc)), is the slowest option at small n. Third, **inline SoA positions make distance nearly free**: 9–12× faster than the gather, and only when vectorised. A generic `x86-64` build fell back to SSE2 and was 1.5–2.3× slower on that loop, and no `target-cpu` is set anywhere in the repo's build or scripts.

The literature backs these choices. Rust's `select_nth_unstable` is introselect with a median-of-medians fallback, so it is O(n) worst case but not branch-free ([Rust core select.rs](https://doc.rust-lang.org/src/core/slice/sort/select.rs.html)). Intel's AVX-512 `qselect` claims up to 15× over `std::nth_element` on 32-bit keys ([x86-simd-sort](https://github.com/intel/x86-simd-sort)), and Faiss built WarpSelect because k-selection, not distance, was its GPU kNN bottleneck ([Johnson et al. 2017](https://ar5iv.labs.arxiv.org/html/1702.08734)). Both are C++ or GPU, though. Once the threshold leaves only O(k) survivors per refill, FFI to a SIMD select isn't worth it. If explicit AVX-512 is ever written for a filter-and-append loop, Zen 4 has a trap: `VPCOMPRESSQ` with a memory destination "imposes a severe performance penalty". The register form followed by a plain store was 70% faster on Genoa, and Zen 5 fixed the penalty ([golang/go 041f564b3e](https://github.com/golang/go/commit/041f564b3e)).

Memory tuning is low value at this scale. Zen 4 has 1 MB of L2 per core ([Chips and Cheese](https://chipsandcheese.com/p/amds-zen-4-part-2-memory-subsystem-and-conclusion)), and the 8534P shares 16 MB of L3 per 8-core CCX ([TechPowerUp](https://www.techpowerup.com/cpu-specs/epyc-embedded-8534p.c3909)). That dwarfs 80 KB of positions, so prefetching, NUMA placement and quantised positions buy little *(derived)*. Processing clients in spatial order improves L1 reuse, as Ihmsen et al. do with Z-order ([Eurographics DL](https://diglib.eg.org/handle/10.1111/v30i1pp099-112?show=full)), but assembly is partitioned by shard (an address hash), so that would mean reshaping the parallel loop for an expected modest gain *(derived, unmeasured)*.

The hard limit is that **all of this still computes N distances per query in a pile.** At ~0.1–0.3 ns per candidate, the projected floor is ~30 ms of CPU per tick, ≈0.5 ms wall on 64 cores *(derived extrapolation)*. That is good, but it is a constant-factor result, and it gets worse as the crowd grows. The local bench also understates real cost. It shows 65 µs per query at n = 10k (≈0.65 s CPU for 10k queries), while 43 ms of wall time on 64 threads implies several times more. Likely causes are the third select, the mid tier, the lower Zen 4c clock and rayon spinning, so treat the bench as a source of ratios only.

## Density-adaptive leaves make each query O(k) regardless of crowd size

Theory offers O(N log N + kN) all-kNN through Vaidya and Callahan–Kosaraju. Vaidya's analysis was later shown to hide a Θ(n²) step ([Ma & Li 2019](https://ar5iv.labs.arxiv.org/html/1908.00159)), and none of these has a practical benchmark at N ≈ 10k. Dual-tree methods give O(N) guarantees ([Curtin et al. 2015](https://ar5iv.labs.arxiv.org/html/1501.05222)) at real complexity. The practical route to the same bound is simpler. The fastest parallel low-dimensional kNN graph builders start each query **at the leaf that contains it** and walk outward with a k-th-distance bound. With bounded leaf occupancy this gives expected **O(k log k) work per query**, and the 2021 zd-tree work reports a 75× parallel speedup on 72 cores, ahead of competitors "by close to an order of magnitude" ([Yesantharao et al.](https://ar5iv.labs.arxiv.org/html/2111.04182)). `walk_rings` already *is* leaf-based search. It fails only because a 32 m leaf can hold 2,500 players. **The fix is to bound leaf occupancy, not to change algorithm families.** This also answers the team's "a better algorithm, not a finer grid" decision. A global finer grid is the wrong move: 4 m cells mean 4 M cells and a 16 MB `start[]`, a 150 m ring walk of ~75² cells in sparse areas, and still ~730 candidates in the pile *(derived)*. A count-bounded leaf that appears only where density demands it is the algorithmic change. It is GROMACS's density-sized cells applied locally ([Páll & Hess 2013](https://ar5iv.labs.arxiv.org/html/1306.1737)).

Concretely, `Grid::rebuild` keeps the 32 m CSR index that every system shares. For any cell whose count exceeds a threshold T (say 256), it runs a second counting sort over that cell's slice into a sub-grid of side ≈ 32 m / ⌈√(count/c)⌉, with c ≈ 25–32 players per sub-cell. This permutes items only *within* the cell's slice, so `for_each_near` and other consumers keep working unchanged. The cost is one more O(N) pass over dense cells' items, parallel per cell. A kd-tree build of 10k points takes ~0.5 ms single-threaded for comparison ([sdd/kd-tree-comparison](https://raw.githubusercontent.com/sdd/kd-tree-comparison/master/all-benchmarks.json)). The query then becomes a **box-pruned ring walk**:

1. Inside the client's own dense cell, walk sub-cell rings first, which sets the threshold τ to roughly d_k quickly.
2. In every later cell, visit only the sub-cells (or the whole cell, if sparse) whose box overlaps the square q ± √τ, and skip any cell whose box min-distance² ≥ τ.
3. Stop when τ ≤ (exact visited-box edge distance)².

The result is exact for the same reason a kd-tree query is: RVO2's kd-tree shrinks its range as neighbours are found and recurses only into boxes within range ([RVO2 KdTree.cc](https://github.com/snape/RVO2/blob/main/src/KdTree.cc)). In the pile, sub-cells of ~2.2–3.5 m holding ~25–65 players mean a query covers 3×3 to 5×5 sub-cells, **~300–800 candidates instead of ~10,000**, a 12–30× cut in distance work. With the threshold, selection runs on ~O(k) survivors *(derived)*. The 200 m disk at 10k benefits too. Its 32 m cells hold ~330 players, and its k-th neighbour sits ~10 m out, so 9 cells (~2,900 candidates) shrink to ~500 *(derived)*. Uniform spread has no dense cells and is untouched.

The alternatives are weaker fits. An off-the-shelf kd-tree is fine on paper. Kiddo v5 builds 10k 2D points in 526 µs and answers 1,000 k = 100 queries in 344 µs of wall time on a 12-core 5900X, roughly 4–8 µs of core time per query ([kd-tree-comparison](https://raw.githubusercontent.com/sdd/kd-tree-comparison/master/all-benchmarks.json)). But that is ~40–80 ms of CPU per tick at 10k, no better than an adaptive grid *(derived)*. It adds a dependency. It splits the networking index from the one grid that the architecture insists NPC proximity and AoE share. And its benchmarks are uniform data only, with nothing on extreme clustering. A Morton-sorted SoA array (an implicit quadtree or LBVH, buildable by one radix sort ([Karras 2012](https://research.nvidia.com/publication/2012-06_maximizing-parallelism-construction-bvhs-octrees-and-k-d-trees))) is a cleaner long-term layout, but it is a bigger rewrite for the same asymptotics.

Temporal coherence adds an exact, cheap refinement, though not a replacement. Seed τ with last tick's k-th distance inflated by 2·v_max·dt. **The result is exact by construction:** if at least k candidates pass the seeded filter, the top k of those are the true top k, because anything rejected is farther than all of them. The motion bound only decides how often the fallback (fewer than k survive) fires *(derived)*. In the pile the seeded radius is (2.5 + 0.43) m, so ~(2.93/2.5)² × 100 ≈ 140 candidates survive per query rather than everything in the first leaves *(derived)*. Full Verlet-style kNN lists (keep k + m candidates, rebuild when displacement exceeds the gap) are the MD standard for fixed cutoffs ([LAMMPS neigh_modify](https://doc.lammps.org/neigh_modify.html); [GROMACS pairlist tuning](https://manual.gromacs.org/current/doxygen/html-full/pairlist__tuning_8cpp.xhtml)). They don't pay off here. The gap between the 100th and 150th neighbour is ~0.56 m in the pile, against 2δ ≈ 0.43 m per running tick, so lists die after about one tick *(derived)*. Kinetic kNN structures assume known trajectories ([arXiv:1412.5697](https://arxiv.org/pdf/1412.5697)) and don't fit erratic player input.

Query-side clustering is the next exact step, if one is needed. GROMACS computes cluster-pair interactions to reuse data and fill SIMD lanes ([Páll & Hess 2013](https://ar5iv.labs.arxiv.org/html/1306.1737)). The kNN analogue, derived by the researchers and unpublished: queriers in a leaf with centre c and radius ρ all have their k nearest within d_k(c) + 2ρ of c. So one gather of that superset S(L), ~325 players for 16 queriers in the pile, serves the whole leaf, and each member only selects k from S(L) *(derived)*. The catch is structural. Assembly runs per shard, and a leaf's clients are spread across shards by address hash, so sharing needs a new parallel pre-pass after the grid rebuild that writes per-leaf candidate sets for assembly to read. Once adaptive leaves land, the remaining saving is ~2× on the walk, so this should wait for a profile.

## Shipped engines rank approximately, which licenses a bounded-error safety net

No engine the researchers examined performs exact per-client kNN. Unreal's Replication Graph exists because per-actor, per-connection relevancy "will bottleneck the server's CPU" at Fortnite's 100 players and ~50,000 actors. It keeps grid-cell actor lists "shared between client connections" across frames ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)), and it adds frequency buckets as node occupancy grows ([UE API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/ReplicationGraph/UReplicationGraphNode_ActorListF-/FSettings)). Iris filters by grid cell, then ranks by a two-sphere distance falloff. Its inner plateau gives every object within 10 m the same priority, so the order inside it is set by accumulated age, not distance, and priority accumulates until sent ([Epic Iris prioritization](https://dev.epicgames.com/documentation/en-us/unreal-engine/iris-prioritization-in-unreal-engine)). Mirror sends a client's 3×3 cells with no distance test, which was 30× faster than distance checks in uMMORPG tests ([Mirror](https://mirror-networking.gitbook.io/docs/manual/interest-management/spatial-hashing)). EVE gives up on selection and dilates time to a 10% floor ([CCP](https://www.eveonline.com/news/view/introducing-time-dilation-tidi); [EVE Uni](https://wiki.eveuniversity.org/Time_Dilation)). PlanetSide 2's 2023 fix replaced "any character in range" NPC sweeps with interaction-focused checks ([MassivelyOP](https://massivelyop.com/?p=429961)).

lattice-net's near tier already ranks with an accumulator, so the exact rank of entity 100 against 101, ~0.05 m apart in a pile, has no gameplay meaning *(derived)*. That makes a bounded-error approximation an acceptable degradation rung. The best candidate is **cell-quantised selection**: take whole sub-cells in order of min-distance until ≥ k players, so every chosen player is within d_k + the sub-cell diagonal, an error of ≤ ~3–5 m in the pile *(derived)*. Another is **stratified id-hash sampling** inside any leaf that exceeds a cap, which mirrors the existing mid/far stagger, so every player is still seen within M ticks. Morton-window kNN with shifted orders has (1+ε) guarantees ([Chan, via Yesantharao et al.](https://ar5iv.labs.arxiv.org/html/2111.04182)), but it needs a different layout. The approximation is not optional in one case: **identical positions.** The sim has no player-player collision (no such code in `sim/src/movement.rs`), and spawn points stack players. Subdivision can't split coincident points, so a leaf at the minimum sub-cell size that still holds thousands needs a hard candidate cap to keep per-query cost bounded. Any approximate mode should be scored against the exact search on sampled clients, with **recall@k, recall@16** (the combat-relevant core), **max missed rank** and **near-set churn per second**. These follow the "neighborship consistency" idea from the VON literature ([Jiang et al.](https://staff.csie.ncu.edu.tw/jrjiang/publication/Enhancing%20Neighborship%20Consistency%20for%20p2p%20distributed%20VE.pdf)). No shipped game publishes such metrics.

Verification should run at three levels. Unit tests require bit-identical results against brute force for steps 1–6, using the packed key's id tie-break so ties compare deterministically. The local microbench records ns per query and candidates per query for pile, disk, blob and uniform after each step, so regressions show up before any rental. Then one bare-metal session (`scripts/cloud-up.sh`, `cloud-run.sh limits` then `full`, always ending with `cloud-down.sh`) checks four things against the 2026-10-04 Scaleway baselines. The pile ramp should stay at L0 under 33.3 ms through 10k with the ladder off; it currently breaks at 7,217. Blob and disk-200m p99 should not regress from 8.5–9.4 ms and 18.95 ms respectively. Uniform-20k assembly should be unchanged. And `perf stat -e branch-misses,instructions` on the pile should confirm the mispredict-bound diagnosis. The next bare-metal session is already planned for the `--sockets` measurements, so steps 0–4 should land before it.

## Conclusion

The pile looked like a call for a new algorithm. It turns out to be the existing algorithm running on a leaf size that ignores density, plus a selection loop that never discards anything. Fixing both restores the O(k)-per-query behaviour that leaf-based kNN guarantees, and none of it touches the decision that one grid serves every system: sub-cells only permute items inside a cell's slice, so NPC proximity and AoE inherit the same index. One consequence matters for M3. Once candidate cost is bounded by k rather than by crowd size, the remaining density risk is coincident positions, and the cheapest structural fix for that is in gameplay, not the index. Player separation, or spawn jitter, would make the exact path always sufficient and keep the approximate rung for genuine overload.

The open questions are empirical. Nobody has measured the adaptive grid's constants on Zen 4c, or the real gap between the local bench and the 64-core box, and the thresholds (T, sub-cell occupancy, minimum side) are educated guesses. The step-0 harness exists to settle them cheaply before any rented hour is spent.
